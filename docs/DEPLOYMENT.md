# Deployment Guide

Deployment target per spec §7.6: a single Docker host ("localhost"), HTTPS
everywhere from Phase 1, one-command bring-up. This guide covers Phase
1a/1b — the backend/portal stack. Endpoint agent rollout is covered
separately (`agent-installer/README.md`).

## Prerequisites

- Docker + Docker Compose v2 on the host
- `openssl` (used by `generate-secrets.sh`)
- `mkcert` — installed automatically by `setup-certs.sh` if missing (spec
  §7.6); requires network access to download it the first time
- Ports 443, 1514, 1515, 55000, 5601, 10051, 8082, 8080, 8081, 4433, 3000
  free on the host (see the port table in the spec §7.6 — every host port
  is already unique, no conflicts to resolve)

## First-time setup

```bash
cd infra
./setup.sh
```

One command. Runs, in order: `generate-secrets.sh` (creates `.env`),
`setup-certs.sh` (installs the mkcert CA + issues every service's HTTPS
cert), `docker compose up -d`, then waits for the portal's `/api/health`
endpoint (the reverse proxy's only backend route is `/api/*`; the backend
`/health` path is reached as `/api/health`) before reporting done. Safe to
re-run — existing secrets/certs are reused, not regenerated (pass
`./setup.sh --force` only for a genuinely fresh install; it will invalidate
an existing deployment's credentials).

If you'd rather run the three steps individually (e.g. to inspect output
between them), `setup.sh` calls exactly these, in this order:
`./generate-secrets.sh` → `./setup-certs.sh` → `docker compose up -d`.

Trust the mkcert CA on any machine that will browse the portal (not just
the Docker host): `setup.sh`/`setup-certs.sh` prints the one-line
`mkcert -install` command to run on each team laptop against the same CA.

### ✅ OCS Inventory — confirmed (session 5)

OCS Inventory (and its `ocs-db`) is **kept** in the stack. It's listed in the
port table in spec §7.6 (host port 8081) but not in §2's main technology
stack table; this session that ambiguity was confirmed as *intended* — OCS
(NG) performs asset discovery/inventory on the Windows fleet and feeds GLPI,
so leaving it enabled is correct. No action needed; the service starts by
default and its secrets are auto-generated by `generate-secrets.sh`.

## Verifying the deployment

```bash
docker compose ps                      # everything should show "healthy" or "running"
curl -k https://localhost/api/health   # portal health check (via reverse proxy)
```

Browse to `https://localhost` — the only URL end users ever see (spec
§7.1). Every backend tool (Wazuh Dashboard, Zabbix, GLPI, Grafana,
MeshCentral) stays behind the portal; their host ports are for admin/agent
traffic only, not general Browse access (see the firewall-scope note in
spec §7.6).

## Portal backend — running tests

This platform was built without network access in the sandbox where it was
written, so dependency-requiring tests were never executed there — only
syntax-checked. On a machine with network access:

```bash
cd portal-backend
pip install -r requirements.txt
pytest -v
```

The 4 test files with zero external dependencies
(`test_version_drift.py`, `test_cleanup_store.py`, `test_agent_commands.py`,
`test_pilot_ring.py`) were actually executed during development and all
passed (5/5, 9/9, 6/6, 9/9 respectively) — re-run them anywhere with
`PYTHONPATH=. python3 tests/<file>.py` as a quick sanity check even without
installing dependencies.

## Self-healing scripts (endpoint side)

PowerShell scripts under `self-healing/` require a Windows host with
PowerShell. They were parsed (0 errors) and PSScriptAnalyzer-clean (0
errors), and the Category B quarantine/restore/purge flows were functionally
executed under pwsh 7.4.6 on this build host using real temp files. The
remaining unverified piece is the actual **agent polling** against a live
portal with an endpoint-specific service token — that needs a Windows endpoint.

```powershell
Install-Module -Name PSScriptAnalyzer -Scope CurrentUser
Invoke-ScriptAnalyzer -Path .\self-healing\*.ps1
```

Then dry-run each script (`-WhatIf` where supported) on a test VM.
`agent-command-poller.ps1` needs a per-endpoint service token — provision
one per the RBAC model in `docs/ARCHITECTURE.md` and schedule the poller
via Task Scheduler (every 1–5 minutes is reasonable; restore/purge are not
latency-sensitive).

## Agent rollout to Windows endpoints

Runs on each Windows PC being monitored, not on this Ubuntu host — see the
root `README.md` for why. Quick path: `agent-installer/one-click-install.ps1`
downloads and installs all three vendor agents in one command. Fleet-wide
GPO/Intune push: the WiX bundle in `agent-installer/wix/`. Either way,
`GET /alerts/rollout-plan` gives pilot-ring-first phased rollout (§7.2.1).
See `agent-installer/README.md` for details.

## Office 365 / Azure AD (SSO + report email)

Both the SSO login flow (`GET /api/auth/sso/login`) and the report email
channel (`alerting.send_report_email`) are implemented against Microsoft's
live endpoints using a stdlib-only OAuth2 client in `app/ms_oauth.py`, so no
extra Python dependency is needed. They are exercised offline (fake config)
in `tests/test_sso_email.py`, but the live token-exchange and Graph calls
must be validated against a real tenant as part of the Phase 0 spike (§6).

Provisioning (first-time, per tenant):

1. Register an application in Azure AD; note its **Client ID**, **Tenant
   ID** and generate a **Client Secret** (app-level permission).
2. Set the redirect URI to `https://portal.aaditech.local/api/auth/sso/callback`.
3. For report email, grant the app the `Mail.Send` application permission.
4. Populate `infra/.env`:
   `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TENANT_ID`.
5. Optional — RBAC: `AZURE_ADMIN_GROUP_IDS` (comma-separated Azure AD
   group object IDs) whose members become **Cleanup Approver** at login
   (§7.1). If empty, every authenticated user is Viewer + Support Engineer
   only (no-one can approve Category B deletions — safe default).

Until these are filled in, `/auth/sso/login` returns a clear
`azure_not_configured` error and `send_report_email` returns `False`; no
network call is made in either case.

## Moving beyond localhost

If the portal ever needs to be reachable at a real public domain (e.g.
`portal.aaditech.com`) instead of just `localhost`/LAN, that's a distinct,
later step — swap the portal's mkcert certificate for a real CA-issued one
(Certbot/Let's Encrypt). See spec §7.6 "Later: moving beyond localhost" —
no backend tool configuration changes, since none of them are ever reached
directly by an end user.
